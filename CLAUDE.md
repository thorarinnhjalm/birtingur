# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Birtingur is a self-service display advertising platform for the Icelandic market aimed at **long-tail niche creators** (e.g. food/lifestyle bloggers), not premium publishers. Publishers register a site, declare its content **categories**, and embed ad slots; advertisers buy by **category + budget** ("ads in `matur` for 50.000 kr"), and the platform spreads impressions across all sites in that category. All money is in **ISK** (integer króna, no decimals); VAT is 24%. The product direction and the category-buying design live in `docs/superpowers/specs/2026-06-04-category-network-buying-design.md`.

## Commands

This is a **Turborepo + pnpm** monorepo. Run from the repo root unless noted.

```bash
pnpm install
pnpm dev          # all apps in watch mode
pnpm build        # turbo build (respects ^build dependency order)
pnpm lint
pnpm typecheck
pnpm test         # all package tests via turbo
pnpm format       # prettier --write
pnpm verify       # format:check && typecheck && lint — runs automatically as the pre-push hook (.githooks/pre-push)
```

Per-package: `pnpm --filter @ada/api test` (also `@ada/dashboard`, `@ada/mcp`, `@ada/serving`, `@ada/shared`, `@ada/snippet`, `@ada/firebase-tests`).

### Tests need the Firestore emulator

`apps/api` and `firebase/tests` run against the Firestore emulator (`vitest.config.ts` hardcodes `FIRESTORE_EMULATOR_HOST=127.0.0.1:8080`, project `ada-test`). The emulator requires a **Java runtime** on PATH (`java -version`); without it these tests fail with "Unable to locate a Java Runtime" before any test runs. Don't run their `vitest` directly unless an emulator is already up. Use the root wrappers, which start/stop the emulator for you:

```bash
pnpm test:api          # runs @ada/api tests inside emulators:exec
pnpm test:rules        # runs Firestore security-rules tests
pnpm emulator          # standalone emulator (firestore:8080, auth:9099, storage:9199, UI:4000)
```

Run a single test file/case: `pnpm --filter @ada/api test -- tests/campaigns.test.ts -t "case name"` — but only with an emulator running (wrap in `firebase --config firebase/firebase.json emulators:exec '...'` otherwise).

`@ada/shared`, `@ada/dashboard`, `@ada/serving`, and `@ada/snippet` tests are plain `vitest` (no emulator). `pnpm test:e2e` runs the dashboard Playwright suite (boots firestore+auth emulators; needs OpenJDK on PATH).

Local data: start `pnpm emulator` in one shell, then `pnpm --filter @ada/api seed` in another to fill it with sample publishers, campaigns, slots, and wallets.

## Architecture

Seven workspaces under `apps/*` and `packages/*` (an eighth, `firebase/tests` = `@ada/firebase-tests`, holds the Firestore security-rules tests). **`@ada/shared` is the dependency root** — every other package builds it first (their `build` scripts run `pnpm --filter @ada/shared build` before `tsc`). Edit shared schemas/types and downstream packages must rebuild to see them.

- **`packages/shared`** — single source of truth. Zod schemas (`schemas/`), TS types, Firestore collection names + typed converters (`firestore/`), ISK/date formatting, and business constants (`constants.ts`: platform fee %, min payout, VAT rate, IAB sizes, frequency caps, cache TTLs). Import everything from `@ada/shared`.
- **`apps/api`** — control-plane REST API. A **Hono** app (`src/index.ts`) mounting `/v1/*` routers. Routes (`src/routes/`) are thin; business logic lives in `src/services/`. Deployed as Vercel functions: the `api/*.js` files are committed JS entrypoints that import from `dist/` (the compiled `src/`). `vercel.json` rewrites everything to `api/index`, plus six standalone functions: the five scheduled crons and `cron-diagnostics` (on-demand ops health check — Redis queue depths, env presence — gated by `CRON_SECRET`, no schedule).
- **`apps/serving`** — hot-path ad serving (ad request, impression, click). Optimized for latency with Redis (Upstash) caching in `src/lib/`. Kept separate from `apps/api` because it has different scaling/latency requirements (V1 Vercel, V2 Cloudflare Worker).
- **`apps/dashboard`** — React 19 + Vite SPA, with `pages/{advertiser,publisher,admin}/` role areas, `locales/` (Icelandic UI), TanStack Query (pinned to 5.40.0 via root `pnpm.overrides`). Styling is Tailwind 4 with brand tokens in the `@theme` block of `src/styles.css` (`bg-primary` navy, `bg-surface-*` families, `rounded-card`, Inter + Material Symbols) — use these, not raw hex. Pages follow the **Nordic-editorial** design language: shared primitives in `src/components/ui/editorial.tsx` (`Eyebrow`, `EditorialH1`, `NumberedSection`, `BigFigure`, `PillButton`, `StepIndicator`) — compose with these instead of hand-rolling the patterns. The approved per-screen designs (with final Icelandic copy) live in `docs/superpowers/specs/2026-07-03-redesign-templates/*.dc.html`; when redesigning a screen, keep its existing TanStack Query hooks/mutations/routes intact and only replace presentation (see `docs/superpowers/plans/2026-07-03-nordic-redesign-implementation.md`, incl. the marketing-claims guardrail: no claims beyond the verified USP list). **SEO prerender**: marketing routes get static HTML at build time via a two-step pipeline (`prerender/README.md`) — `prerender:capture` (dev-only, Playwright) renders every `public/sitemap.xml` route into the committed cache `prerender/snapshots.json`; the Vercel build's `scripts/prerender-apply.mjs` stitches those into fresh `dist/<route>/index.html`. The sitemap is the route source of truth; **re-run capture and commit `snapshots.json` whenever marketing copy, those pages, or the sitemap change**, or crawlers keep seeing stale content. **`prerender:capture` renders the built `dist/`, not your source**, so always `pnpm --filter @ada/dashboard build` first. It now refuses to run when any file under `src/` (or `public/sitemap.xml`) is newer than `dist/index.html` — before that guard existed, capturing against a stale build silently rewrote `snapshots.json` with the previous build's copy and reported success. The API and serving apps deliberately serve `Disallow: /` robots.txt — only the dashboard is indexable.
- **`apps/mcp`** — MCP server, scoped per API key: publisher-scoped keys get the publisher tool set (create/manage ad slots, fetch embed snippets, set content policy, handle approvals, read stats), advertiser-scoped keys get the advertiser tool set (list categories/inventory, check wallet + purchase limits, list approved creatives, buy category campaigns, read campaign status), `both`-scoped keys get everything. `createMcpServer` resolves the key's scope by calling `GET /v1/api-keys/me` over HTTP (`src/lib/api-client.ts`) — the MCP server has no direct DB access — and registers no tools at all if that call fails. This deliberately supersedes the earlier publisher-only design (commit 6973955 removed advertiser tools entirely): agentic buying is safe now that the committed-funds reservation gate and daily reconciliation cron exist (see `docs/superpowers/plans/2026-07-27-advertiser-mcp-agentic-buying.md`). Agentic purchases carry hard guardrails, opt-in per API key (`purchase.enabled`, `services/api-keys.ts`): a `monthlyCapIsk` derived from summing `budget.totalIsk` over campaigns tagged `createdVia.apiKeyId` this calendar month, and an `autoApproveLimitIsk` above which a purchase is created `pending_approval` (tagged `pendingReason: 'agent_purchase'`) with an in-app + email notification, awaiting the owner's approve/reject in the dashboard (`POST /v1/campaigns/:id/approve|reject`, dashboard/ID-token only — an `ak_` key can never approve its own pending purchase). Top-ups, budget increases, and refunds remain dashboard-only; there is no MCP path that adds money. `Idempotency-Key` support on `POST /v1/campaigns` makes agent retries safe. The MCP server also sends an `X-Ada-Channel: mcp` header on campaign creates, stored as `campaign.createdVia.channel` — this is self-reported provenance only (any raw `ak_` key caller could set the same header), never a security boundary: every gate that actually matters (purchase gating, `rejectApiKeyMutation`, monthly-cap scoping) keys off `apiKeyId`'s presence/ownership, not `channel`, which exists purely so create-time notifications/logs can distinguish "via MCP" from "raw API key" for observability. **Transport**: `src/index.ts` builds a fresh `McpServer` + `WebStandardStreamableHTTPServerTransport` per `/mcp` request, so the server is stateless by construction (no session store, load-balancer safe); auth is a static `Bearer ak_` header (no OAuth/Dynamic Client Registration) and none of roots/sampling/logging are used. That is what makes the MCP `2026-07-28` spec revision (stateless core, plus deprecation of legacy HTTP+SSE and of roots/sampling/logging on a 12-month window) a low-impact migration here — don't reintroduce the legacy SSE transport. The real SDK floor is `1.25.0`, the first release shipping `server/webStandardStreamableHttp.js`; as of 2026-07-29 npm's latest `@modelcontextprotocol/sdk` (`1.30.0`) still reports `LATEST_PROTOCOL_VERSION = '2025-11-25'`, so there is nothing to upgrade to yet.
- **`packages/snippet`** — the `<script>` publishers embed, built with esbuild (not tsc); size-budgeted (`pnpm --filter @ada/snippet size`). Served from CDN.
- **`packages/widgets`** — Web Components (`adplatform-stats`, `adplatform-approval-queue`, `adplatform-campaign-stats`) for embeddable publisher stats and admin UI, also esbuild. The `apps/serving` build copies the output to `public/v1/widgets.js`.

### Cross-cutting concepts

- **Auth** (`apps/api/src/lib/auth.ts`): `Authorization: Bearer <token>`. Two token kinds — Firebase ID tokens (dashboard users, `scope: 'both'`) and API keys prefixed `ak_` (programmatic/MCP, verified in `services/api-keys.ts`, `scope: 'advertiser' | 'publisher' | 'both'`). Admin status comes from `ADMIN_EMAILS` or `@adplatform.is` domain. There is no demo bypass token — the old `demo-mock-token` backdoor was removed entirely (commits 21b1b29 / 0c0c70a); don't reintroduce one. `requireScope('advertiser' | 'publisher')` gates advertiser-owned routers (`campaigns`, `creatives`, `advertisers` (profile), `wallet`) and publisher-owned routers (`publishers`, `slots`) against a mismatched `ak_` key scope — Firebase ID tokens are always exempt. An `ak_` key additionally needs `purchase.enabled` (see the `apps/mcp` bullet above) to create campaigns at all.
- **Firestore** (`apps/api/src/lib/firebase.ts`): firebase-admin, auto-switches to emulator when `FIRESTORE_EMULATOR_HOST` is set. Collections: `publishers, slots, advertisers, creatives, campaigns, ledger, payouts, stats, notifications, generated_previews`.
- **Ad model (category-based)**: a publisher has `categories` (1..n from `AD_CATEGORIES` in `@ada/shared`); slots inherit them. A campaign's `targeting.categories` (not slotIds) decides where it serves. `apps/api/src/lib/push-cache.ts` resolves campaigns→slots by category intersection at cache-build time, so the serving hot path (`apps/serving/src/lib/select.ts`) just reads `slot.activeCreatives` from Redis. CPM is **locked** server-side to `FLAT_CPM_ISK` (`createSlot` ignores client price). `GET /v1/categories/inventory` gives the per-category daily-impression forecast shown in the buy flow.
- **Serving ↔ snippet contract (cross-origin)**: the `packages/snippet` embed runs on the **publisher's** origin but fetches from `apps/serving` at a different origin (`SERVE_BASE`, baked in at esbuild time). `/v1/ad` returns tracking URLs (`clickUrl`, `impressionPixel`) **relative** to the serving origin; `render.ts` must resolve them against `SERVE_BASE` or they 404 on the publisher domain (impressions go uncounted). The impression pixel fires only after a viewability delay (IAB standard). Frequency capping uses a **first-party** visitor id the snippet stores in publisher-origin `localStorage` (`getVisitorId`, consent-gated) and passes as `?vid=`. **Serving sets no cookies at all** — `?vid=` is the only visitor identifier, and `getVisitorToken` returns `''` when it is absent rather than minting a server-side id, so an unconsented request is capped by nothing and records nothing (`routes/impression.ts` skips `recordVisitorImpression` on an empty token). The old `_adp_v` cookie was removed: the serving origin differs from the publisher's, so any cookie it set was cross-site (`SameSite=None`) and falsified the cookie-free guarantee the marketing copy makes. Don't reintroduce a `Set-Cookie` here — `tests/ad-route.test.ts` asserts its absence on both the fill and no-fill paths. When no campaign fills, the slot's `fallbackType` decides what renders: `house_ad` (default, Birtingur house creative) or `transparent` (invisible placeholder); both still fire signed impression pixels.
- **Money flow**: advertiser wallets are an append-only **ledger** (`services/ledger.ts`, `wallet.ts`). Serving fans out each signed event to **separate Redis queues** (`logEvent` in `serving/src/lib/analytics.ts`): every event → `events:stats`, impressions also → `events:accrual` — separate lists because the two crons are independent consumers and a shared list let one cannibalize the other's events (`events:queue` is the drained legacy list). CPM spend accrues on a cron (`/api/cron-accrue`, every 15 min) draining `events:accrual` — gross **per publisher** is `round(FLAT_CPM_ISK * count / 1000)`, the campaign is charged the sum of those grosses (conserves money), publisher credited net of the 20% platform fee. The cron decrements `campaign.budget.remainingIsk` (the enforced cap); `budget:{id}` in Redis is the real-time serve-time gate. Stats aggregate hourly (`/api/cron-aggregate`); publisher payouts run monthly (`/api/cron-payouts`, manual bank transfer marks them complete). Cron endpoints are gated by `CRON_SECRET`. Click/impression events are HMAC-signed (`serving/src/lib/crypto.ts`) and deduped (`seen:{sig}`) to block replay/fraud. **Budget gate is fail-closed** (`serving/src/lib/analytics.ts`, `getRemainingBudgets`): a missing/expired `budget:{id}` key is read as `0`, so the campaign stops serving until the next cache-refresh cron reseeds it — better to under-serve than over-spend (commit `d76b72b`). If Redis itself is unreachable the serving handler throws and `/v1/ad` returns 500 (no ad), which is also fail-closed. **Cron alerting** (`services/ops-alerts.ts`): each cron records a Redis `heartbeat:{name}` on success and calls `alertCronFailure` from its catch (email via Resend + in-app admin notification + console, deduped 6h per cron via `alerted:{name}`); the hourly `cron-aggregate` doubles as a dead-man's switch (`checkCronHeartbeats` — stale heartbeat past its schedule+grace threshold → alert; missing keys bootstrap silently). Recipients: `OPS_ALERT_EMAILS` (falls back to `ADMIN_EMAILS`). `/api/cron-diagnostics` also reports heartbeat ages (pull-based). Campaign create/increase is gated server-side on a **committed-funds reservation** (`services/wallet.ts`, commit `ae2297b`): available = ledger balance − `remainingIsk` still committed to the advertiser's other fund-holding campaigns, checked in a Firestore transaction serialized by a `fundsVersion` write on the advertiser doc, so concurrent creates can no longer oversubscribe a wallet (`INSUFFICIENT_FUNDS`). Expired campaigns release their hold (10-min sweep in `cron-refresh-cache` plus an `endsAt` exclusion in the committed sum). A daily cron (`/api/cron-reconcile`, `services/reconciliation.ts`) independently cross-checks the ledger against `campaign.budget.remainingIsk` and the Redis `budget:{id}` counter and alerts ops on drift, without ever mutating money state itself.
- **Payments**: Teya (card top-ups) under `services/teya/` with `http.ts`/`webhook.ts` and a `stub.ts` for tests; Payday/Blikk is the invoicing/bookkeeping integration (see `docs/superpowers/plans/2026-06-03-10-payday-blikk-integration.md`). Both follow a real-impl + `stub.ts` pattern.
- **Auto-scan** (`services/auto-scan/`; the related `domain-classifier.ts` sits directly in `services/`): classifies publisher domains (uses `GEMINI_API_KEY`) during approval; also has a `stub.ts`.
- **AI advisor** (`services/ai-advisor.ts`): generates personalized tips for advertisers using Gemini; falls back to rule-based tips if `GEMINI_API_KEY` is absent.
- **Notifications** (`services/notifications.ts`): in-app notification system stored in Firestore; routes can create notifications for `advertiser | publisher | admin` roles.
- **Widget keys** (`services/widget-keys.ts`): separate auth tokens (not `ak_` API keys) scoped to embedding the `packages/widgets` components on external pages.
- **AI creative assistance** (`services/ai-creative/`) is a split, wizard-driven flow (creative-wizard, `docs/superpowers/plans/2026-07-27-creative-wizard-flow.md` — supersedes the original one-shot `/v1/creatives/generate`): `POST /v1/creatives/generate/copy` (`copy.ts`) SSRF-guards and scrapes the advertiser's landing-page URL and writes 1–3 Icelandic copy variants via Gemini (text only — no rendering/uploads), persisting a manifest (Firestore `generated_previews/{advertiserId}`) with `status: 'copy'` and empty per-variant `images`. `POST /v1/creatives/generate/render` (`render-variant.ts`) then renders ONE chosen variant for a caller-supplied, non-empty subset of `IAB_STANDARD_SIZES` plus a `bold`/`light` template: an optional abstract background generated once via Gemini, one of the two Nordic-editorial SVG templates (`templates.ts`) per size via `@resvg/resvg-js` (fonts from `@expo-google-fonts/inter` — `@resvg/resvg-js` only loads ttf/otf font files, not `@fontsource`'s woff/woff2), uploaded to Firebase Storage; an optional `editedCopy` REPLACES the variant's copy wholesale (marked `edited: true` on the manifest) — user-edited copy bypasses the Gemini claims guardrail by definition, so the responsibility confirmation + auto-scan at confirm time are the designed backstop. `POST /v1/creatives/generate/confirm` (unchanged external contract) turns the advertiser's picked (rendered) variant into real `Creative` docs via the normal `createCreative`/auto-scan flow — confirming a variant that's still `status: 'copy'` (no rendered images) 400s. Without `GEMINI_API_KEY`: copy falls back to rule-based text, backgrounds fall back to flat color blocks — the pipeline is fully key-less. Rate-limited per advertiser per day in independent buckets (`lib/rate-limit.ts`, fail-closed when Redis is configured, skipped when it isn't): `gen-copy` 20/day, `gen-render` 10/day. `GET /v1/categories/sizes?categories=a,b` (`services/inventory.ts`'s `getCategorySizeForecast`, IAB-sizes-only and Redis-cached 10min) is the wizard's read-only "which sizes will I get" insight, feeding the size step before any copy/render call — like `/inventory`, it's read-only aggregate data behind `requireAuth`; `requireScope('advertiser')` only restricts `ak_` API keys to the advertiser scope, so any authenticated ID-token (dashboard) user can read it regardless of role, not just advertisers.

## Conventions

- **ESM throughout.** Relative imports inside a package must use the `.js` extension (e.g. `from './routes/publishers.js'`) even though the source is `.ts`.
- Vercel function entrypoints (`apps/api/api/*.js`) are intentionally compiled JS pointing at `dist/` and are excluded from the typecheck tsconfig — don't convert them back to TS (see recent commits e4259e2 / 67d0335).
- Specs and implementation plans live in `docs/superpowers/specs/` and `docs/superpowers/plans/` — consult them before building a feature. Key specs: category buying (`2026-06-04`), budget pacing (`2026-06-06`), brand safety + forecasting (`2026-06-10`), Nordic-editorial redesign (`2026-07-03`). Deeper system design (data model, Mermaid flow diagrams, accounting) is in `docs/architecture.md`; Vercel/Firebase/Upstash setup is in `docs/deployment.md`.
- **`ds-bundle/`** (repo root) is the synced mirror of the "Birtingur UI Kit" Claude Design project — no app code imports it, so don't wire it into builds. Its `README.md` documents the kit's usage conventions (tokens, editorial primitives, Icelandic copy rules) and is the reference when translating designs into `apps/dashboard`.

## Secrets / env vars

Required vars must be set or the app fails; optional vars degrade to a documented fallback (handy for local dev and for reading the code).

**`apps/api`** — Required: `FIREBASE_PROJECT_ID`, `FIREBASE_CLIENT_EMAIL`, `FIREBASE_PRIVATE_KEY` (admin credentials), `CRON_SECRET` (gates all cron endpoints), and Redis (`UPSTASH_REDIS_REST_URL` + `UPSTASH_REDIS_REST_TOKEN`, or the `KV_REST_API_URL`/`KV_REST_API_TOKEN` aliases). Optional: `RESEND_API_KEY` (absent → emails logged to console, see `services/mail.ts`), `GEMINI_API_KEY` (absent → AI advisor + auto-scan fall back to rule-based/stub), `TEYA_API_KEY` (absent → wallet top-ups return 503 unless `TEYA_STUB=true` explicitly opts into the fake-payment stub — never set that in prod), `TEYA_BASE_URL`, `TEYA_WEBHOOK_SECRET`, `ALLOW_PREVIEW_CRONS` (absent/anything other than `'true'` → money-flow crons 403 on Vercel preview deploys, see `lib/preview-guard.ts`), `ADMIN_EMAILS` (comma list; also `@adplatform.is` domain grants admin), `SENDER_EMAIL` (defaults to `onboarding@resend.dev`), `FIREBASE_DATABASE_ID` (defaults to `(default)`), `FIREBASE_STORAGE_BUCKET` (defaults to `<projectId>.firebasestorage.app` — the post-2024 Firebase default; set only if the project uses the legacy `.appspot.com` bucket), `APP_BASE_URL`, `CDN_BASE_URL`.

**`apps/serving`** — Required: Redis (same vars as API) and `SIGNING_SECRET` (HMAC for click/impression signatures; must match what the API uses to build pixels). Optional: `NODE_ENV`/`PORT`, plus a built-in demo slot when `NODE_ENV=development`.

**`apps/dashboard`** — Required: the six `VITE_FIREBASE_*` vars (see `.env.example`). Optional: `VITE_API_BASE` (defaults to `http://localhost:3001`).

## Deployment topology

Each app is a separate deploy (prod domains under `birtingur.app` — NOT the `adplatform.is` naming that appears in older docs/code comments): dashboard → `www.birtingur.app`, API → `api.`, MCP → `mcp.`, serving → `serve.` (Vercel V1, Cloudflare Worker V2). Vercel project names are `birtingur-{api,dashboard,mcp,serving}`. Note: the dashboard project skips builds when a pushed commit touches nothing under `apps/dashboard` (ignored build step) — an empty retrigger commit will report deploy "success" without shipping new dashboard code. The snippet is a static artifact on Cloudflare R2/CDN (`cdn.adplatform.is/v1/snippet.js`). Firestore + Redis (Upstash) are the `ada-prod` project/database. The five crons (`cron-accrue` every 15 min, `cron-aggregate` hourly, `cron-refresh-cache` every 10 min, `cron-payouts` monthly, `cron-reconcile` daily; see `apps/api/vercel.json`) run on Vercel schedules and are the only writers of accrual/stats/payouts — `cron-reconcile` is the exception, it's read-only and only alerts on drift.

**Preview deploys**: Vercel builds a preview on every PR, but **crons only fire on production** — previews never run accrual/aggregation/payouts on their own. Previews share the same `ada-prod` Firestore/Redis unless you point their env vars elsewhere, so the five cron entrypoints are guarded fail-closed (`apps/api/src/lib/preview-guard.ts`, wired into `cron-accrue`/`cron-aggregate`/`cron-payouts`/`cron-refresh-cache`/`cron-reconcile`): hitting them on a deploy where `VERCEL_ENV === 'preview'` now returns `403 { error: 'preview_blocked' }` instead of running. To exercise the money flow against a preview, first point that preview's env vars at an isolated staging Firebase project + Redis database (see `docs/deployment.md`), then set `ALLOW_PREVIEW_CRONS=true` on the preview environment and hit the cron endpoints manually: `curl -H "Authorization: Bearer $CRON_SECRET" https://<preview-url>/api/cron-accrue`. `cron-diagnostics` is unguarded (read-only, no schedule) and safe to hit on any preview.
