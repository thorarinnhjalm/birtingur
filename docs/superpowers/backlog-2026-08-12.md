## 1. cron-aggregate drains a fixed 5 x 1000 events per hourly run

Correction to how this item was first framed: the cron carrying the
"falls behind under a traffic spike" bug is **cron-aggregate**, not
cron-accrue, and it is **not** in the money flow.

- cron-accrue is already fixed (`39a214c` -> `0f62cfd`). `drainAndAccrueAll`
  loops `drainBatch` until the queue is dry, bounded both by `maxBatches`
  (20 x 500) and by a 45s wall-clock deadline under the function's 60s
  `maxDuration`, re-queues events when a campaign fails, and reports
  `capped` / `timedOut` / `netDrained` so an operator can tell truncation
  from a clean finish. There is nothing left to do there.
- `apps/api/api/cron-aggregate.js` still has the pre-fix shape: a hand-rolled
  `for (let i = 0; i < 5; i++)` around `drainAndAggregate(1000)`. The ceiling
  is 5000 events per hourly run, there is no wall-clock deadline, and the
  truncation is reported nowhere an alert can see it (the response body
  carries `batches`, which no monitor reads).

Consequence: sustained traffic above ~5000 stats events an hour makes
`events:stats` grow permanently, and the numbers on the dashboard drift
further behind reality every hour. This is reporting, not billing —
`events:accrual` is a separate Redis list drained by cron-accrue, so spend,
ledger and payouts are unaffected. Severity is "wrong numbers on screen",
not "wrong money".

Second, related hole: the backlog-growth watcher inside
`checkCronHeartbeats` measures only `EVENT_QUEUE_ACCRUAL`
(`apps/api/src/services/ops-alerts.ts:28`, alert threshold 500). Nobody
watches `events:stats` depth, so this exact failure mode is invisible: the
cron keeps recording a green heartbeat while falling further behind.

### The trap the review found, so the port does not repeat it

Whoever moves the accrual drain loop into the aggregator has to carry these
four across. Each one was a review finding on the accrual side, in order of
how expensive it is to get wrong:

1. **Check the deadline only between batches, never mid-batch.** Vercel
   killing the function mid-batch takes the batch's already-popped,
   not-yet-written events with it. The deadline exists so the loop stops
   itself first, with everything either written or safely back on the queue
   (`apps/api/src/services/accrual.ts:504-513`).
2. **The aggregator has no re-queue at all today.** `drainAndAggregate` pops
   up to `batchSize` events and calls `aggregateEvents(events)`; if the
   Firestore batch commit throws, those events are simply gone
   (`apps/api/src/services/stats-aggregator.ts:436-458`). The accrual path
   re-queues via `safeRequeue`, and refuses to re-queue once the charge is
   committed. Adding a loop multiplies the number of events exposed to this,
   so the re-queue has to land in the same change, not as a follow-up.
3. **Report progress, do not assume it.** `drained` counts events popped;
   `netDrained = drained - requeued` counts events that actually made
   progress. A run that pops 5000 and writes none must not be able to look
   like a success — that is what the `netDrained === 0 && drained > 0` alert
   in accrual.ts exists for.
4. **Upstash `rpop` returns already-parsed objects, not strings** (`1d4b7f3`,
   where this silently dropped events). The aggregator handles it correctly
   today; keep the `typeof raw === 'string'` guard through any refactor.

## 2. The dead-man's switch hangs off a single cron — owner decision

`checkCronHeartbeats()` is called from exactly one place:
`apps/api/api/cron-aggregate.js`. The watchdog for all five crons therefore
runs inside the hourly cron that item 1 identifies as the most likely one to
be unwell. If cron-aggregate stops firing, nothing alerts about anything
else, and the other four — including the money crons — can die silently.

Proposal on the table: move the call to `cron-refresh-cache` (every 10 min),
which also drops detection latency for the other crons from ~1h to ~10 min.

Recommendation: **call it from both, rather than moving it.** Moving
relocates the hole instead of closing it — whichever single cron hosts the
watchdog, that cron's own death silences the watchdog. Two callers close it
for the pair, and duplicate calls are already harmless: staleness alerts
dedupe per cron name for 6h (`alerted:{name}`, `ops-alerts.ts:23-24`), and
apart from bootstrap writes `checkCronHeartbeats` is read-only. Thresholds
are per-cron (`CRON_STALENESS_MINUTES`) and need no change; calling the check
more often cannot make a fresh heartbeat look stale.

One thing to know while testing it: the dedupe key is shared between the
staleness alert and `alertCronFailure` for the same cron, so within a 6h
window whichever fires first suppresses the other. Pre-existing behaviour,
unchanged by adding a caller, but it will look like a missing alert.
