## 1. cron-aggregate cannot keep up, and drops events when the write fails

Two corrections to how this item was first framed, both worth keeping as a
record of how the memo went wrong.

**First:** the cron carrying the "falls behind under a traffic spike" problem
is **cron-aggregate**, not cron-accrue, and it is **not** in the money flow.
cron-accrue was fixed in `39a214c` -> `0f62cfd`: `drainAndAccrueAll` loops
until the queue is dry, bounded by `maxBatches` and a 45s deadline, re-queues
on failure, and reports `capped` / `timedOut` / `netDrained`. Nothing left to
do there. `events:stats` is reporting, `events:accrual` is billing, and only
the latter is money — so the severity here is "wrong numbers on screen", not
"wrong money".

**Second:** this memo was written against a stale `main`. While it sat
unmerged, PRs #29 to #31 (2026-08-11/12) rewrote much of this file, so the
"fixed 5 x 1000 with no deadline" shape it described was already gone. What
`main` has now: chunked `rpop(key, count)` reads with raw-count short-read
handling, a 30s wall-clock deadline checked between batches, `capped` /
`timedOut` reporting, and a `chunkedBatch()` write phase that commits every
~450 operations instead of once. The 504-every-hour failure from 2026-08-11 is
genuinely fixed.

What was still missing, and is what this branch adds:

- **The 5000-event ceiling survived the fix.** `maxBatches` was still 5 at
  1000 events a batch, so any hour busier than 5000 stats events still grew
  `events:stats` permanently — the deadline stopped the run from being killed,
  but not from falling behind. With a deadline in place the batch cap only
  needs to be a runaway-loop backstop, so it is now 20.
- **There was no re-queue at all.** `rpop` removes events before anything is
  written, so a failed write dropped up to a full batch. The cron 500'd and
  alerted, so the failure was visible, but those events were gone and their
  hour stayed permanently short.
- **Truncation only reached a `console.warn`.** True, and better than nothing,
  but nobody who is not already reading Vercel logs sees it.

Related hole, still open: the backlog-growth watcher inside
`checkCronHeartbeats` measures only `EVENT_QUEUE_ACCRUAL`
(`apps/api/src/services/ops-alerts.ts:28`, alert threshold 500). Nothing
watches `events:stats` depth over time; the alerts added here fire per run,
which covers the same ground from the other direction but is not the same
signal.

### The trap the review found, so the port does not repeat it

Whoever moves the accrual drain loop into the aggregator has to carry these
four across. Each one was a review finding on the accrual side, in order of
how expensive it is to get wrong:

1. **Check the deadline only between batches, never mid-batch.** Vercel
   killing the function mid-batch takes the batch's already-popped,
   not-yet-written events with it. The deadline exists so the loop stops
   itself first, with everything either written or safely back on the queue
   (`apps/api/src/services/accrual.ts:504-513`).
2. **The aggregator has no re-queue at all.** `rpop` removes the events
   before the write phase starts, so a failed commit dropped them. The accrual
   path re-queues via `safeRequeue`, and refuses to re-queue once the charge is
   committed. Raising the batch cap multiplies the events exposed to this, so
   the re-queue had to land in the same change, not as a follow-up.
3. **Report progress, do not assume it.** A run that pops 5000 events and
   writes none must not be able to look like a success — that is what the
   zero-progress alert in accrual.ts exists for.
4. **Upstash `rpop` returns already-parsed objects, not strings** (`1d4b7f3`,
   where this silently dropped events). `toEventList` on main handles it; keep
   the `typeof item === 'string'` guard through any refactor.

A fifth trap, specific to the current `main` and NOT present on the accrual
side: `aggregateEvents` no longer commits atomically. `chunkedBatch()` commits
every ~450 operations, so "the write failed" does not imply "nothing was
written", and blindly re-queueing a failed batch would apply the increments of
every chunk that did land a second time. Stats carry no per-event dedup, so
there is no way to recover from that after the fact.

**Landed:** `maxBatches` is 20 (the 30s deadline is the real bound; the cap is
now only a runaway-loop backstop). `drainStatsBatch` re-queues a batch when
nothing was committed, and refuses to when something was — `chunkedBatch.commit`
settles every chunk and throws `AggregationError` carrying `anyCommitted`, so
the drain can tell the two apart. Events it cannot retry are counted as `lost`
and alerted, never dropped silently. Truncation, zero progress and lost events
all page ops (deduped 6h) instead of only reaching a `console.warn`. The
`recorded:{hour}` counter step was made non-throwing, so a post-write Redis
blip can never be misread as "nothing was committed".

## 2. The dead-man's switch hangs off a single cron — owner decision

`checkCronHeartbeats()` is called from exactly one place:
`apps/api/api/cron-aggregate.js`. The watchdog for all five crons therefore
runs inside the hourly cron that item 1 identifies as the most likely one to
be unwell. If cron-aggregate stops firing, nothing alerts about anything
else, and the other four — including the money crons — can die silently.

Proposal on the table: move the call to `cron-refresh-cache` (every 10 min),
which also drops detection latency for the other crons from ~1h to ~10 min.

Recommendation: **call it from both, rather than moving it.** Moving
relocates the hole instead of closing it — whichever single cron hosts the
watchdog, that cron's own death silences the watchdog. Two callers close it
for the pair, and duplicate calls are already harmless: staleness alerts
dedupe per cron name for 6h (`alerted:{name}`, `ops-alerts.ts:23-24`), and
apart from bootstrap writes `checkCronHeartbeats` is read-only. Thresholds
are per-cron (`CRON_STALENESS_MINUTES`) and need no change; calling the check
more often cannot make a fresh heartbeat look stale.

One thing to know while testing it: the dedupe key is shared between the
staleness alert and `alertCronFailure` for the same cron, so within a 6h
window whichever fires first suppresses the other. Pre-existing behaviour,
unchanged by adding a caller, but it will look like a missing alert.

**Landed:** `cron-refresh-cache` is now a second caller of
`checkCronHeartbeats()`, isolated in its own try/catch the same way the
expired-campaign sweep is, so a failing watchdog cannot take down the cache
refresh that keeps ads serving. cron-aggregate keeps its call.
